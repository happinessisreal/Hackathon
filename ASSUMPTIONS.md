## Phase 1 - data model additions beyond the literal locked schema block

The CLAUDE.md schema block is the source of truth for structure; two nullable columns were added because specific locked *rules* require data the literal column list didn't include a place for. Both are additive/non-breaking:

- `readings.anomaly BOOLEAN DEFAULT 0` - required by the out-of-order rule: "a reading with `ts_device` earlier than the zone's last applied reading is stored + flagged anomaly, never rewrites current state" (TC18c). There's nowhere else to put this flag without a schema addition.
- `zone_transitions.reason TEXT NULL` - required by the override endpoint contract: "manual state set **with reason**". `cause` distinguishes sensor/manual; `reason` carries the admin's free-text justification for that specific manual transition.

## Phase 1 - sensor payload semantics

- **Rule 1 ("zone nodes send raw numbers, never a state or score") is interpreted as**: nodes may report a *normalized* physical reading (0.0-1.0 for gas/water, computed from ADC + the MQ-2 datasheet range in firmware) - this is a raw sensor value, unit-converted like a thermistor-to-Celsius conversion, not a derived state or score. Nodes never compute SAFE/WARNING/CRITICAL or a risk_score; only the backend fusion formula does. This reading matches the DB column names (`gas_norm`, `water_norm`) and the validation examples given verbatim in CLAUDE.md ("negative water / gas > 1.0" - i.e. the *normalized* field is what's range-checked).
- **Per-sensor offline**: a payload field that is `null`/omitted means that specific sensor is offline for this reading. Pydantic fields are `Optional`; only out-of-range *non-null* values are rejected with 422. The zone card shows an OFFLINE badge if any hazard sensor is offline; the fusion formula treats a missing reading as a 0 contribution (never fabricates SAFE by treating "no data" as "safe").
- **Gas warm-up boot time**: the ingest payload includes an optional `uptime_ms` field (milliseconds since the node's `millis()` reset), which is realistic ESP32 firmware behavior. `boot_ts = ts_server - uptime_ms/1000`, **recomputed on every reading** (not just the first) when `uptime_ms` is present - Phase 3's driver caught that a one-time-only version (set on first reading, never touched again) can never re-arm warm-up after a real reboot within the same server process, since a client claiming a smaller `uptime_ms` later doesn't change anything once `boot_ts` is already set. Recomputing every time is actually simpler *and* correct: in continuous operation `now` and `uptime_ms` advance together so the candidate stays ~constant, but an actual power-cycle (uptime_ms resets near 0) makes it jump forward and correctly re-arms the 30s window - no separate "reboot event" needed. If `uptime_ms` is omitted entirely, warm-up falls back to a one-time "assume freshly booted" at first sight (so it still naturally elapses after 30s instead of blocking gas forever).
- **On backend restart**: boot time cannot be recovered from the DB (uptime isn't persisted per reading), so a restart conservatively re-arms the full 30s gas warm-up window rather than risk trusting a stale/incorrect boot estimate. This is a deliberate fail-safe bias, not an oversight.

## Phase 1 - state machine mechanics (not pinned to exact numbers by CLAUDE.md, only behavior)

- **Fire debounce**: exactly 5 consecutive HIGH raw readings (as CLAUDE.md states literally) trigger a jump to full contribution (level 1.0), not a gradual ramp - CLAUDE.md only specifies decay-on-removal as gradual, not rise. At 750ms/reading this is ~3.75s, not the case doc's paraphrased "0.75-1s"; the literal "5 consecutive readings" rule was treated as authoritative since it's precisely testable, and the timing prose reads as an approximation.
- **Fire decay**: on raw HIGH->LOW after being debounced-on, contribution decays linearly from its current level to 0 over 5s (wall-clock based, recomputed on read, not a discrete step function). Re-triggering (5 more consecutive HIGHs) during decay snaps back to 1.0 and cancels the decay.
- **Occupancy (PIR) hold**: applied symmetrically to both the *risk-formula input* and to "loggable" state - a raw PIR flip only becomes the stable `occupancy_factor` after holding continuously for 1.5s, whether entering or leaving occupied. This was extended from "logged only if held ≥1.5s" to also gate the fusion input, so a flickering PIR can't cause the risk score (and therefore transitions/incidents) to jitter either.
- **Admin override semantics**: sets the zone to the exact requested state (SAFE/WARNING/CRITICAL) immediately, bypassing hysteresis for that one transition, and follows normal incident open/resolve rules. It is a point-in-time correction, not a lockout - the very next sensor reading re-evaluates normally via the real formula and hysteresis. This matches "manual state set" as a discrete action rather than a persistent mode, and avoids a manual override permanently masking a real, currently-reported hazard.
- **Concurrency**: sensor ingestion and admin override for the same zone serialize on an in-process `asyncio.Lock` keyed by zone_id, so a same-instant race can't double-fire a transition/incident/actuation for one state entry. Documented as a single-process assumption; the scaling section notes the Postgres/Redis path needed for multi-worker deployment (TC11 doc requirement).

## Phase 2 - WS, dashboard, and two real bugs caught by testing it live

- **Datetime bug (found via the WS test, fixed at the ORM layer)**: SQLite drops tzinfo on read, so any `DateTime` column loaded back from the DB came back naive while every freshly-created timestamp in the app is UTC-aware - comparing them raised `TypeError: can't subtract offset-naive and offset-aware datetimes`. This wasn't cosmetic: it would have broken `priority.py`'s unacked-seconds calc *and* `restore_from_db` (rule 6, TC9a) the moment either touched a DB-loaded timestamp after this point in the build. Fixed once at the source with a `UTCDateTime` `TypeDecorator` (backend/models.py) that normalizes every datetime through the ORM boundary, rather than patching each comparison site. Regression-covered by `tests/test_restart_recovery.py`.
- **`asyncio.Lock` is bound to the event loop that created it**: `ZoneManager`'s per-zone lock (backend/zone_manager.py) deadlocks if used from two different loops - which only happens when two independent `TestClient` instances (each spinning its own thread+loop) touch the same zone concurrently. A single uvicorn worker only ever has one loop, so this is a testing artifact, not a production bug (see `tests/test_ws.py::_FakeWebSocket` docstring) - but it's exactly the kind of thing that would bite on a naive multi-threaded deployment, so it's called out here rather than silently worked around.
- **Priority queue delivery**: as decided in Phase 1, embedded in `GET /api/zones/status` and in every WS payload under `priority_queue` - never a separate endpoint.
- **WS push strategy**: immediate broadcast on `state_change`/`incident_ack` (real, meaningful events) plus a 1s periodic broadcast (keeps unacked-seconds escalation and risk scores moving between readings without broadcasting on every 750ms sensor POST at scale - see TC11). Every push carries the *full* canonical snapshot (backend/status_service.py), never a delta, so the dashboard is never asked to reconstruct state from partial events (rule 2).
- **Zone payload additions beyond Phase 1**: `open_incident_id` and `incident_status` per zone, and `value` per sensor (the zone's last raw reading for that sensor type). Needed so the dashboard can wire ack buttons and sensor mini-readouts directly from the snapshot without extra round-trips, without inventing any client-side derivation of state/score.
- **CSS `[hidden]` bug (found live in-browser, not by pytest)**: `#login-view { display: flex }` and `.modal { display: flex }` both match the native `[hidden] { display: none }` UA rule in specificity (ID beats it outright; class-vs-attribute ties and the later same-specificity rule wins) - so toggling `.hidden = true` from JS was silently ignored and the login form/modal stayed visually present underneath the dashboard. Fixed with a global `[hidden] { display: none !important; }` rule. This only surfaced by actually loading the page in a browser and screenshotting it - worth remembering that pytest's 45 green tests said nothing about this.
- **Zone-grid re-render bug (also found live)**: the 1s periodic snapshot was rebuilding the *entire* zone grid via `innerHTML = ""` every tick regardless of whether the data changed, which reliably destroyed in-flight button interactions (proven by Playwright's click retries failing repeatedly against a real running server). Fixed by skipping the rebuild when `JSON.stringify(zones)` is unchanged from the last render (frontend/js/app.js).
- **Session persistence**: token/role/username cached in `localStorage` so a page refresh doesn't force a re-login; a 401 on the first post-refresh request clears it and falls back to the login view.

## Phase 3 - sim/ driver, and real bugs the driver caught that pytest couldn't

The driver's job is footage + demonstrability, not re-proving correctness pytest already owns (formula math, hysteresis, dedup, ack races, restart recovery all stay in tests/). Each scenario checks one observable and prints narration cues. Even so, running the real system end-to-end over real HTTP surfaced three genuine bugs no unit test would have caught:

- **Gas warm-up couldn't survive a real reboot.** The original `boot_ts` logic set it once (first reading ever, per zone, per process lifetime) and never touched it again - so a device that actually power-cycled mid-run could never re-arm its 30s warm-up window; the backend had no way to tell a reboot from continued operation. Fixed in `backend/pipeline.py` by recomputing `boot_ts = now - uptime_ms/1000` on **every** reading instead of only the first: in continuous operation this stays ~constant (`now` and `uptime_ms` advance together), but an actual power-cycle (uptime_ms resets near 0) makes the candidate jump forward and correctly re-arms warm-up, with no separate "reboot event" needed. Falls back to a one-time "assume fresh boot" only when a node never reports `uptime_ms` at all, so it still naturally elapses after 30s instead of blocking gas forever.
- **`ZoneNode.seq` starting at 0 collided across scenarios.** Dedup on `(zone_id, seq)` is permanent for the DB's lifetime, but each scenario calling `ctx.node("IoT Lab")` got a *fresh* `ZoneNode` object that also started counting from `seq=0` - so a later scenario's readings silently collided with an earlier scenario's already-stored seq numbers and were dropped as duplicates (visible only as an unexplained "score didn't change"). Fixed by seeding `ZoneNode.seq` from wall-clock time at construction instead of 0 (`sim/node.py`) - a real device's counter never resets just because your test harness holds a new reference to it. The same class of bug existed in `sim/scenarios.py`'s protocol-level tests (tc6c/6d/6e, tc18a), which used hardcoded literal seq numbers that would have silently broken on a second run against the same DB - fixed with a timestamp+counter-based `_seq_base()` (CLAUDE.md requires every scenario to be idempotent/re-runnable for video retakes, and a hardcoded seq quietly violates that on rerun #2).
- **Phantom-zone cleanup left the delete blocked.** `ON DELETE RESTRICT` triggers on the *existence* of a referencing row, not its status - so resolving an incident's status before deleting a zone does nothing; the incident row itself (and zone_transitions, and readings) still block the delete. `sim/common.py::delete_phantom_zones` now actually deletes rows in FK dependency order (acknowledgments -> incidents -> zone_transitions -> readings -> sensors -> zone) instead of trying to "resolve around" the constraint.

All three were found by literally running `sim/driver.py` against a live server and reading what came back - not by code review. Validated against a throwaway DB/port (`data/scsrg_scenario_test.db`, port 8801), never against the demo server on :8000, so a live judge/demo session is never disturbed by an automated validation pass. `sim/driver.py --phantom 30` (TC11a): 30 concurrent phantom zones, 0 errors, p95 latency ~460-810ms across runs, cleaned up completely afterward (verified zero orphan rows). `sim/seed.py --readings 10000`: ~0.6s to insert, the TC19 indexed incidents query stayed at ~14ms on 300+ seeded incidents.

**Cut per cost/benefit**: TC23e (restart recovery) is not driver-orchestrated (no subprocess kill/restart of uvicorn from within the driver). The DB-level recovery logic is already proven by `tests/test_restart_recovery.py`; the video demonstrates it as a manual restart step instead - automating process lifecycle management from the driver was the clearest gold-plating candidate under the time budget.

## Phase 4 - firmware, and the validation gap that comes with it

Unlike Phases 1-3, this one **cannot be end-to-end validated from this environment** - there's no Wokwi simulator or real ESP32 hardware to run it against. What was done instead, ranked by how much confidence it actually buys:

- **Wire protocol cross-checked field-for-field** against `backend/schemas.py` (`IngestPayload`/`CommandOut`) and against `sim/node.py` - the same protocol, already proven "ALL GREEN" against the real backend in Phase 3. The `.ino` sends exactly `{seq, fire, gas_norm (omitted when ZONE_HAS_GAS is false), water_norm, occupancy, ts_device, uptime_ms}` and parses `{buzzer, relay, led}` from the command response, same as the Python reference implementation.
- **Wokwi part types and pin names verified against live sources**, not recalled from training data: fetched `docs.wokwi.com` part-reference pages for `wokwi-gas-sensor`, `wokwi-pir-motion-sensor`, `wokwi-buzzer`, `wokwi-relay-module`, `wokwi-potentiometer`, `wokwi-pushbutton`, and pulled a real, currently-live official Wokwi example project's `diagram.json` (`wokwi.com/api/projects/305566932847821378/diagram.json`, by Wokwi's own creator) to confirm the exact ESP32 board type string (`wokwi-esp32-devkit-v1` - **not** `board-esp32-devkit-v1`, which seemed equally plausible from the docs alone and turned out to be wrong) and the pin-naming convention (`esp:D26`, `esp:GND.1`, `esp:TX0`, matching the silkscreen labels in `wokwi-boards/boards/esp32-devkit-v1/board.json`).
- **No native Wokwi part for a flame sensor or a water-level sensor** - confirmed by checking the supported-hardware list, not assumed. Substituted a `wokwi-pushbutton` (flame - click-and-hold simulates sustained flame for the debounce/decay cases) and a `wokwi-potentiometer` (water level - same substitution pattern used for the MQ-2 gas sensor before Wokwi added a real one). Both clearly labeled in `diagram.json` and documented in `firmware/README.md`'s wiring table so a judge reading the pin table isn't confused by a pushbutton standing in for a flame sensor.
- **A real Arduino gotcha caught by manual re-read, not a compiler** (none available for ESP32 code in this environment, and installing the toolchain was judged low ROI relative to a human Wokwi smoke-test being required either way): `"/api/commands/" + String(ZONE_ID)` starts the concatenation chain with a raw `const char*` literal on the left of a `String` - Arduino's `WString.h` only defines `operator+` overloads with `String`/`StringSumHelper` on the *left* side, not `const char* + String`, so this line as originally written would not have compiled. Fixed to `String("/api/commands/") + ZONE_ID`.
- **Strapping pins avoided on principle**: GPIO 0, 2, 5, 12, 15 can select the wrong ESP32 boot mode if an external component holds them high/low at power-on. Wokwi's simulator has no opinion about this (it would "work" in simulation regardless), so it's exactly the kind of bug that ships to real hardware unnoticed. All outputs (LEDs, buzzer, relay) and inputs (flame, PIR) use non-strapping GPIOs instead - see `firmware/README.md`'s pin table.
- **`ts_device` needs real wall-clock time, not millis()-since-boot** - `configTime()` against NTP is called in `setup()` before the first reading, gated on a "did this actually sync" check (`time(nullptr)` still near-1970 means not yet synced). Without this, every reading's `ts_device` would be ~1970-01-01, and the incident timeline (TC14) and out-of-order/anomaly detection (TC18c) both key off that field.
- **`localhost` is unreachable from Wokwi's simulated network.** This isn't a code bug but is the single most likely thing to derail a demo recording if discovered late: `BACKEND_HOST` is a named config constant specifically so the fix (point it at an `ngrok`/`cloudflared` tunnel, or a temporary public deploy) is a one-line change instead of a firmware rewrite - see `firmware/README.md` "Reaching the backend from Wokwi". Surfaced here and in the root README now, not left for the video-recording session to discover.

**What this section can't claim**: that the sketch actually compiles under the Arduino/ESP32 toolchain, or that it behaves correctly once running. Both require a human to open the project in Wokwi and press play - flagged plainly in `firmware/README.md` rather than folded into an "ALL GREEN"-style claim this phase can't back.

- **Bonus 2 delivery**: `trend` (scores/slope/rising) is embedded directly in every zone entry of `build_zone_status_payload` (backend/status_service.py) rather than left as a separate per-zone poll - the same "one canonical snapshot, WS and REST never disagree" rule from Phase 1/2 applies here too (rule 2). - **Bonus 4 advisory-boost storage is in-memory only**, on `ZoneRuntime.advisory_reports` (backend/zone_manager.py) - a list of `(severity, received_at)` pruned as it decays, not a new DB table. The locked schema additions so far (`readings.anomaly`, `zone_transitions.reason`) were both required because a *rule* needed somewhere to persist a flag; NL reports don't need durability across a restart (they're a soft, actively-decaying triage hint, gone after 10 minutes regardless), so adding a table would be schema growth without a corresponding requirement. If judges want an audit trail of raw report text, the `/api/report` response and future server logs are the record; not added here to keep scope matched to the spec's "soft advisory term" framing.
- **Bonus 4 validation gate applies identically to both the LLM path and the fallback path** - a hallucinated zone name from the LLM is rejected by the exact same `validate_and_clean()` a keyword-parser miss would hit (backend/nl_report.py). - **LLM failure/timeout falls through to the offline parser even when a key is configured**, not only when the key is absent. The spec's literal fallback trigger is "if no API key"; extended to "if no key OR the call errors/times out (8s cap)" so a flaky network or a DeepSeek outage during the actual recording can't turn a live demo into a 500 - the deterministic gate runs identically either way, so this doesn't weaken validation, only availability.
- **Advisory boost only ever touches zones `priority.py` already restricted to CRITICAL** (via sensor data) - it re-orders that queue, never populates it, and is added nowhere near `risk_score`/state/`/api/commands`. - **Playwright synthetic clicks intermittently failed to trigger the NL-report form's native `submit` event in this sandbox** (`browser_click`/`page.locator().click()` landed on the correct element per `elementFromPoint`, but no `click` *or* `submit` listener fired) while the exact same click mechanism worked fine for the login form earlier in the same session. Isolated by dispatching a real `SubmitEvent` on the form directly, which fired the handler correctly and completed a full round trip (fetch -> backend parse/validate -> `ZoneRuntime.advisory_boost` -> the priority queue's justification line updating live to `... + NL report +6 = ...` in the running dashboard). Logged as a tooling quirk of this particular MCP/CDP sandbox, not an application bug - the underlying code path is confirmed working by both the direct-dispatch test and 12 new passing pytest cases in `tests/test_nl_report.py`.

**Bonus 3 (ML prediction) - modeling decisions worth remembering**:
- First training run: 1.6% positive rate, precision/recall 0.0 - the model learned "never predict positive". Root cause is structural: with the locked weights, CRITICAL (>=65) is *unreachable without fire* (gas 25 + water 25 + occ 10 = 60), so "predict CRITICAL" is really "predict ignition", and a spark from nowhere is unpredictable by definition.
- Fix was physical realism, not metric-gaming: smoldering precedes flame (flux fumes, battery off-gassing - the case's own lab hazard profiles), so ~35% of synthetic episodes model a slow (~2 min) gas rise with ignition planted >= the 120s label horizon into it - meaning the entire window the model must predict actually contains visible precursor signal. No-precursor sudden fires stay in the data so the model remains honest about what it cannot foresee. This assumption is stated in ml/train.py's docstring and DOCUMENTATION.md §12(a), not hidden.
- Per-channel slope features (gas_slope/water_slope over the last 8 samples) added to match CLAUDE.md's original feature spec; `ZoneRuntime` now keeps matching `recent_gas`/`recent_water` windows so runtime features are computed by the same `compute_slope` used in training.
- Final held-out metrics: accuracy 0.837 / precision 0.449 / recall 0.863 at an F1-optimal threshold (0.498) chosen on a separate validation split. The high-recall/moderate-precision point is deliberate for an early-warning advisory and documented as such - the case grades "soundness and honesty", and these are the honest numbers.
- Serving is pure Python (sigmoid over JSON-exported coefficients) - no sklearn/numpy/pickle at runtime; sklearn is a train-time-only dependency in requirements.txt.
- Safety (3e) is enforced structurally, not by promise: `backend/prediction.py` is imported only by `status_service.py`, and `tests/test_prediction.py::test_no_actuation_module_imports_prediction` source-scans pipeline/state_machine/fusion/commands/ingest and fails if anyone ever imports prediction there. The chip is hidden on CRITICAL zones (live alarm supersedes a forecast) and on OFFLINE zones.
